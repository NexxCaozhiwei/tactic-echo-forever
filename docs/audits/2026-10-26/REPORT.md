# TEF 2.0.1代码审计报告

日期：2026-10-26。审计对象：本地提交`9a6aa2f22468b4f9c7df93d34a6c83b0788810fb`，版本`2.0.1`。

## 结论与范围

本次发现12项需要处理或决策的问题：3项高优先级缺陷、1项高优先级契约偏差、7项中优先级问题、1项低优先级文档与证据问题。优先处理技能组额度隔离、HUD只读性和输入部分失败后的清理，再处理派发边界、初始化容错及诊断。

现有测试全部通过，但新增最小复现仍能观察到错误行为。不能据此把当前版本认定为不存在逻辑缺陷，也不能把离线复现等同于已经观察到游戏内故障。

审计覆盖插件的配置清洗、职业与方案、策略、推荐、列表与技能组、增益维护、运行意图、派发、传输、事件入口、HUD与Studio关键路径，以及TEK的协议门禁、派发、输入恢复、设置、物理输入监听和交付脚本。采用静态调用链检查、既有回归和新增隔离复现；这不是所有界面组合、职业技能或Windows环境的穷举验证。

本轮只新增本报告及复现附件，不修改现有业务代码、版本或游戏安装，不提交或推送，不启动、停止或替换活动TEK。没有读取本轮游戏落盘，也没有执行真实SendInput。报告中的“确认”指代码路径与离线复现确认。

## F01：父列表与技能组没有隔离使用额度

位置：`Tactic Echo Forever/SkillGroups.lua:52`的`Begin`、`:34`的`Restore`，以及`Tactic Echo Forever/SequenceUsage.lua:49`的`UsageEligibility`、`:64`的额度读取。

额度使用目标或战斗上下文加`context.index`标识步骤。进入技能组只替换`e.steps`并把索引重置到1，未为`e.usage`建立父列表与组列表的独立作用域。恢复时也没有对应的额度空间恢复。

最小场景：父列表第1项设为每目标使用一次，成功后进入位于第2项的技能组；组内第1项也设为每目标使用一次。父列表已经写入该目标的索引1额度，组内第1项随即被认为已经用过。

R03实际结果：进入组后直接处于组内第2项`2136`，组内第1项`205`没有任何成功回执却被跳过。该复现使用公开战斗与同一目标，不依赖CDM。

建议：以稳定的列表／组实例／步骤身份划分使用额度，不能只使用可复用的数字索引；明确组循环是否共享同一“每目标／每战斗”额度。保留暂停、维护插入及恢复时各自的上下文。

修复验收应覆盖父步骤与子步骤同索引、两个不同组同索引、维护插入、组循环以及目标／战斗周期变化，确认跳过不制造成功计数。

## F02：HUD候选预览会改变运行策略

位置：`Tactic Echo Forever/Recommendation.lua:58`的`HUDSteps`及`:90`的`ManualPolicy`调用；`Tactic Echo Forever/Dispatch.lua:120`附近的策略快照；`Tactic Echo Forever/APL/Custom.lua:571`的`ObservePolicy`。

列表循环的HUD预览会为后续候选调用运行用的`ManualPolicy`。该函数构造的状态没有`readOnly=true`，随后`Check`可以调用`ObservePolicy`。在运行意图开启时，如果一次触发策略明确不满足，后者会清除`record.consumed`，重新武装该条目。

R10先把第2项的一次触发额度标为已消费，当前仍停在第1项；仅调用`HUDSteps`后，额度从`true`变成`nil`。没有成功回执、用户重置或明确的运行策略观察调用。

影响：预览刷新可能改变之后是否再执行该技能；HUD的显示路径因此参与授权。隐藏HUD不应改变运行语义，目前却存在由显示调用带来的额外观察机会。

建议：HUD使用明确只读的求值路径，避免与运行用策略缓存混用；重新武装只能由运行层负责观察。不能只在HUD外层阻止输入，因为副作用发生在策略记录本身。

验收：相同事件、相同条件变化下，对比开启HUD、隐藏HUD、关闭预览及反复刷新HUD，最终额度和派发结果应完全一致。

## F03：输入部分失败缺少主键释放

位置：`tek/src/windows_sendinput.py:184`的部分失败结果、`:195`的`release_modifiers`；`tek/src/engine.py:328`及`:354`的异常恢复。

普通按键计划包含主键按下和抬起。Windows仅接受部分输入时，代码进入失败处理，但恢复函数忽略传入的计划，始终只发送CTRL、ALT、SHIFT、WIN的抬起。

R08使用假的原生接口模拟`2`的两事件计划仅接受1个事件。恢复序列仅包含四个修饰键的抬起，没有`2`的抬起。生产异常分支调用的就是这个恢复函数。

确认的是恢复缺口；本轮没有制造真实Windows部分输入失败，也没有证明用户此前手柄不能跳跃就是该问题。若主键按下已经生效而抬起未生效，当前恢复无法主动解除它，重复按键或鼠标中键同理需要考虑。

建议：记录TEK本次计划可能按下且尚未确认释放的键，按输入计划进行有界清理；清理失败应保留明确告警及阻断。不要扩大为无条件释放所有物理按键，也要避免错误解除玩家此刻真实按住的修饰键。轮滚没有对应抬起，不应混用同一处理。

验收：用假的原生接口逐个覆盖不同截断点、修饰组合和中键；另行进行可控的Windows恢复验收，不能以本次假接口结果替代。

## F04：普通来源脱战派发与当前契约冲突

位置：`Tactic Echo Forever/Runtime.lua:119`的`OutsideCombatAllowed`、`:122`的`CombatAllowed`，以及`Tactic Echo Forever/Dispatch.lua:647`起的`Packet`。

当前约束要求普通战斗来源确认公开战斗，脱战例外仅限用户手动开启的增益维护。实现则额外允许手动模式下的普通来源脱战运行，`maintenanceManual`也同时被用于普通来源授权。

R01在`combat=false`、没有维护接管的情况下，手动模式最终发布非零Token`5`，运行状态为`running`。`tests/run.lua`的`manual_mode_out_of_combat_runs`还明确保留了这一行为，说明它是实现中的有意功能，不是默认模式误读。

这项应按“契约偏差”处理，不能直接宣称手动模式产品设计必然错误。若普通来源必须战斗内，需统一Runtime与最终Packet的门禁并修改对应回归；若希望保留普通技能脱战手动尝试，应先明确扩大授权范围、拆开维护与普通来源的授权字段，再同步当前约束及用户文案。默认自动模式仍有脱战待命门禁，不能把本项泛化为默认登录就直接派发。

## F05：下一步引导技能的排队边界依赖单个ID

位置：`Tactic Echo Forever/Dispatch.lua:335`，`CastQueueWindow`的下一步筛选。

当前代码排除了5019、6603、75和5143，但没有根据下一步的已确认施放类型排除所有引导技能。现有职业目录将奥术飞弹标为引导，用户实际使用的其他等级ID并非5143。

R04配置当前普通读条116、下一步飞弹5144，处于合法提前量内，返回下一步索引2、`WINDOW_OPEN`。这确认了引导边界没有完整实现；没有证明该次排队一定被游戏接受、打断当前读条或成功施放。

建议：将排队能力定义为可检查的资格，不再以单个飞弹ID代表全部引导。类型未知时不授予提前排队，普通执行资格仍由现有链决定。不要使用当前没有引导来代替“下一步不是引导”的证据。

验收应至少包括不同飞弹等级、其他职业引导、地面引导、普通读条、即时技能及未知类型，并保留两次精确回执的归属保护。

## F06：无效维护条目可使初始化整体失败

位置：`Tactic Echo Forever/Maintenance.lua:38–39`，`Initialize`构造`seen`集合。

`CleanRows`会把无效ID保留为带`invalid`标记的条目，但该条目可能没有`spellID`。维护初始化不检查这一点，直接执行`seen[row.spellID]=true`。

R12传入一条`spellID=0`且已经停用的维护条目，`Engine.New`仍失败，报`Maintenance.lua:39: table index is nil`。超过容量形成的无ID错误占位也属于需要覆盖的输入。

建议：区分有效身份、可编辑的无效占位和空配置；无效条目应明确显示、停用或隔离，不能使整个插件初始化失败，更不能自动转换成无条件维护。保存时拒绝非法配置不能替代重载时的防御性清洗。

验收：无效ID、缺字段、错误类型、超过容量、已停用条目、其他职业维护数据异常，均应保持插件可初始化且不授予输入资格。

## F07：CDM无关类别的错误会污染精确结果

位置：`Tactic Echo Forever/APL/PublicConditions.lua:233`，类别失败后覆盖整个同种请求集合的循环。

一个增益请求会遍历图标与增益条两个类别。即使已经从图标帧得到精确且公开的活动值，增益条类别没有目录条目、但该面板不可用时，代码仍将全部增益请求覆盖为未知。

R05图标中精确400588帧一直公开可见且活动；增益条目录为空。仅把无关的`BuffBarCooldownViewer`设为不可用，结果即由`true`变为`nil / CDM_VIEWER_UNAVAILABLE`。

建议：分别记录类别是否公开完整、目录中哪些请求与其相关，再聚合精确匹配的证据。已知为空的类别不应污染其他类别的精确结果；目录未知、重复身份冲突或相关帧受限仍须保留未知。不能通过“取第一个非空值”掩盖真正的冲突。

该问题与400588无关，影响通用CDM增益读取；冷却类别使用相同聚合方式也应检查。本项是条件性可用性问题，不代表当前客户端一定缺少增益条面板。

## F08：策略诊断在重载和组内路径中不完整

位置：`Tactic Echo Forever/Sequence.lua:118`的历史原因码清洗；`Tactic Echo Forever/Dispatch.lua:143`的`manualPolicySnapshot`；`Tactic Echo Forever/APL/Trace.lua`的APL证据记录。

第一处：运行层会记录`UNKNOWN:custom:strategy`等包含冒号或小写字母的原因码，重载清洗却只接受`^[A-Z_]+$`。R06证明该条原因在重新创建Engine后消失。独立队列日志可能保留同一原因，但它依赖配置、容量与对应事件，不能证明主诊断历史完整。

第二处：组内步骤作为列表路径执行，具体条件证据位于内存中的`manualPolicySnapshot`。APL完整追踪没有自动覆盖该快照，普通／队列日志也没有持久化策略序号、条件ID与CDM采样原因。因此现场可能只能看到“策略未知”，无法区分缺目录、帧隐藏、受限值或冲突。

建议：为原因码制定统一白名单规则；对组内和普通列表的阻断持久化有界公开标量，带会话、代次、步骤、回执序号、条件身份和精确原因。不能持久化帧对象、Secret或异常对象；无需增加计时器或新的输入路径。

验收：同一阻断在列表、组内、APL及维护路径中都能定位，重载后仍保留；旧日志清洗、容量截断与跨代失效要有独立回归。

## F09：桌面设置缺省恢复会覆盖无关用户意图

位置：`tek/app/settings_store.py:68`的`from_dict`、`:99`的整体回退、`:103`的整数转换、`:271`的`load`。

R07b：用户设置`auto_start_ui_linked=false`，同时一个采样间隔字段写成非法字符串，整个配置回退到默认值，自动启动变为`true`。这不是按字段恢复缺省，而是丢弃所有本来有效的设置。

R07：JSON数字`1e309`会解析为非有限值，转换整数产生`OverflowError`；当前只捕获`TypeError`、`ValueError`，异常可以越过设置加载。其他整数转换及布局缓存清洗也需要同类审查。

建议：按字段进行类型、有限性和范围验证，仅修复错误字段；自动启动等用户意图不能因无关字段损坏而恢复成开启。保留恢复原因和旧文件副本，并明确哪些错误需要阻断启动、哪些可以局部恢复。不要简单捕获所有异常后静默返回整套默认设置。

验收：单字段损坏不改变已关闭的自动启动、白名单及进程名；覆盖空值、字符串、布尔值、非有限数字、损坏JSON和布局缓存异常。

## F10：同一Packet重复进行CDM实时完整扫描

位置：`Tactic Echo Forever/Dispatch.lua:647`起的`Packet`，其显式`APL:Allowed`调用及`:672`之后的`ContinuousEvidence`；`Tactic Echo Forever/APL/Engine.lua:178`的策略采样。

连续APL路径在Packet里先直接调用`Allowed`，随后`ContinuousEvidence`又调用一次`Allowed`。每次都会重新采样选中规则的CDM目录与帧。两次复查之间没有通过同一调用上下文复用已验证的结果。

R09在一个带单个CDM增益条件的有效APL封包中，单次`Packet`调用产生4次类别接口调用，即两轮图标／增益条扫描。还未计入Tick、推荐采样及Request路径的其他复查。

这是已经确认的重复工作，而非已确认的游戏帧率瓶颈。若单独按20Hz持续调用该路径，理论上每秒80次类别接口调用，目录逐项读取和帧枚举另计；本轮没有用这个理论值冒充实机耗时。

建议：建立仅限当前Packet调用的校验上下文，在代次、步骤、回执序号、策略修订、绑定和意图均未变化时复用；最终发布前仍核对身份与门禁。不能为了减少扫描直接删除派发前复查，也不能跨封包长期复用受限状态。

验收：记录同一封包的接口调用次数和状态变化注入结果，再单独在实际客户端测量耗时与内存分配。

## F11：可复现部署依赖本机临时脚本

位置：`Tactic Echo Forever/scripts/deliver.py:12`的固定`TARGET`以及`main`仅有的`--deploy`开关。

正式脚本固定写入`C:\Program Files (x86)\World of Warcraft\_cn_beta_\Interface\AddOns\Tactic Echo Forever`，没有目标目录参数。当前项目实际使用的安装目录在`E:\World of Warcraft\_cn_beta_`。此前可用的本机部署方式依赖未受版本控制的`work/`辅助脚本；新的干净检出不能复现该步骤。

本轮没有执行这个固定目标的部署，因而没有改写另一安装目录。问题是交付入口缺少必要配置能力；若机器上存在另一个安装，固定路径还可能使用户更新了错误客户端。

建议：增加明确目标参数或项目本地部署配置，并在任何备份、移动或复制前校验解析后的绝对路径、客户端标识与AddOns边界。保留备份、TOC及逐文件哈希验证，不碰WTF，也不替换活动TEK。该改造不需要自动扫描整机目录。

## F12：文档入口及回执描述已经漂移

位置：`docs/README.md:3`仍把1.2.4标为“当前基线”；`Tactic Echo Forever/scripts/deliver.py:80`写入`continuous_default_enabled=false`；`Tactic Echo Forever/Runtime.lua`的`Clean`实际默认连续输出开启。

R11实际缺省为`mode=auto`、`autoStart=true`、`ordinaryContinuous=true`。回执没有区分“连续输出偏好默认开启”与“初始化时尚未进入连续运行”，其字段不能直接解释为当前配置默认值。根README的边界段落笼统写“隐藏保持未知”，后文才说明增益条目自动隐藏的例外，也容易造成误解。

建议：当前行为集中维护一份，并由真实配置构造回执字段；历史文档明确标注当时版本和已被替代的契约。中文语言扫描只能检查部分英文段落，不能证明版本、语义和验收状态一致。

## 已核对的设计限制与语义债务

以下事项不作为本轮新发现的执行缺陷，也不应未经产品确认就恢复或扩大功能：

1. **已退休条件。** `Custom.CleanRows`主动移除旧`requireReady`及法力字段；`tests/custom_apl.lua`还明确验证了这种迁移。因此不能把R02简单归因于忘记赋值。问题在于旧条件会静默消失，用户难以看出原规则已改变。建议提供迁移说明或可见的已移除标记；是否重新提供对应条件另行决定。内置规则的显式公开0/0检查与自定义已退休字段要分开描述。
2. **原生手柄边界。** 当前BindingToken、按键计划与物理接管围绕键盘、部分鼠标输入建立，没有通用原生手柄输入与手柄接管检测。不能把键盘监听正常解释为原生手柄已受同等保护，也不能根据本轮代码检查解释用户此前全部手柄异常。新增手柄协议或输入后端需要单独设计，不能顺带修改现有线格式。
3. **全职业接入与职业包覆盖。** 自定义主动技能可通过精确已学身份接入；内置职业规则与维护识别并不等于所有职业、天赋、等级和增益都有实机验证。陌生技能仍可能需要目标类型修正或公开CDM目录身份。
4. **距离与人数。** 姓名板与距离探针是有界观察，不是全场敌人数。一次采样最多支持4种人数半径，超出后返回`PROBE_CAPACITY`；界面允许构建更多组合，建议保存前给出容量提示。支持的半径档位不应表述成逐项已实测。
5. **CDM活动信号。** 本次自动隐藏修复保留了精确身份、父面板可见及公开活动值等条件；它不表示所有隐藏帧都代表无增益，也不表示CDM活动值就是光环真值。层数条件继续按已移除处理。
6. **新安装默认内容。** 法师默认列表仍带116、205、205、143等历史等级实验组合，其他职业缺省为空。虽然这是确定的缺省行为，但它不是按当前角色生成的推荐方案。建议首次使用明确标注示例、提示逐项确认精确已学ID；不要用最高ID或同名技能自动授权替换等级。
7. **界面可测试性。** 工作台已集中布局，但旧编辑器、兼容命令、缓存、别名页面仍共同维护状态。建议逐步明确“草稿／已保存配置／只读采样／运行状态”的所有者并减少跨层写入。本次没有把文件较长本身列为缺陷，也没有把用户明确验收的10×10方案按钮当作不合规范问题。
