# 派发生命周期节奏第一阶段

日期：2026-11-09。用户授权P1～P4修改与本地部署，实测后再决定提交和同步；版本保持2.0.1。

## 已实现范围

- P1：复用Transport原有心跳，每0.10秒只检查一次移动值。状态变化使APL采样失效并撤回未完成请求，当前起始和成功回执身份不删除。可在高级TEK页关闭“移动变化重新判断APL”。规则继续使用已有的不限、仅静止、仅移动条件，不硬编码职业技能。
- P2：薄节奏接口位于Runtime，提供 `DispatchTiming:Phase/CanRequest/CanQueue/RetryDecision`。阶段及决策只供解释，不替代Dispatch门禁，不直接输入。诊断页及HUD主图标悬停显示阶段；`queueDiagnostics`沿用512条有界日志，阶段和决策变化才新增节奏记录，排队记录包含当前技能、候选、剩余时间及实际窗口。
- P3：沿用已有排队开关和提前窗口，扩展到Custom APL。必须有当前精确起始、公开普通读条、合法剩余时间及客户端窗口。候选只在窗口内按当前状态求值，不模拟未来资源、光环或成功；同一施法和采样代次缓存准备结果。派发前重新检查选中规则、实时资源和范围、目标身份及配置代次。一次原施法最多保留一次提前尝试。
- P4：已确认的施法或回执归为等待；失败后Custom APL使采样失效并在原重试流程中重新求值，固定序列保留同一步重试。沿用0～0.50秒失败间隔、默认0.15秒及未知时钟阻断；诊断区分 `WAIT`、`REEVALUATE`、`RETRY` 和可派发的 `READY`。

排队候选不会在原施法成功前覆盖当前推荐；只有原技能精确成功后才接续候选与已保留的第二次起始。若下一次成功先于原成功到达，继续按既有保护拒绝，不推测推进。失败、迟到事件及重复事件不增加成功次数。

## 限制

技能组、增益维护、内置APL、引导、魔杖、自动攻击和自动射击不开放提前排队；特殊规则额度不属于首阶段队列范围。普通列表原排队逻辑继续保留。瞬发没有伪造读条窗口；不查询GCD/61304，不增加计时器、钩子或输入链。

本阶段没有实现P5目标变化快速重算、P6实机调参或P7技能组排队。目标身份变化会阻断已有排队请求，但不会据此宣称P5已完成。

## 实机测试

1. `/reload`，在自定义APL给读条技能加“仅静止”，给瞬发技能设置“不限”或“仅移动”。手动开启派发，测试移动后是否更换候选；当前已经起手的技能仍等待真实结果。
2. 在高级TEK页开启普通读条末尾排队，提前窗口先设0.20秒。使用普通读条，检查窗口外没有提前请求；候选未满足、目标改变或接口未知时不提前输入。
3. 分别测试两次同ID、不同ID候选与失败重试；次数只能由各自精确成功推进。引导、技能组和魔杖不应提前请求。
4. 诊断页和主图标悬停查看阶段；测试后重载或退出游戏落盘，检查队列日志中的 `TIMING_*`、窗口、候选与起始／成功身份。

离线检查与部署哈希不证明游戏内排队成功或输入间隙改善。该版本为待用户实测的工作区候选，不提交、不推送。
