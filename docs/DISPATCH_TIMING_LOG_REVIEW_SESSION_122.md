## 三、移动状态下存在反复失败与固定重试开销

保留区间有15条带原事件的`CONTINUOUS_MOVEMENT_FAILURE_RETRY`：奥术愤怒3条、奥术冲击7条、火焰冲击5条。该原因另有15条状态日志，不能把30条原因记录解释成30次游戏失败。区间第一条已经是事件后的派生日志，所对应原始`GAME_EVENT`已被覆盖。

连续且未经过目标重置的例子中，失败到下一次请求约151～199毫秒，符合150毫秒配置加现有心跳调度。没有证据表明这部分属于网络传输延迟。

代码核对发现两个问题：

1. `Dispatch:ContinuousEvidence`检查目标、范围、可用性和资源，但没有对普通组内读条建立独立的公开移动施法资格。可用性为真并不证明该次读条在移动中能够起手，因而可能出现“提出请求 → 客户端失败 → 等待150毫秒 → 再请求”的循环。仍须考虑瞬发触发与明确移动施法例外，不能简单禁止移动时的所有技能。
2. 失败路径只要当时`IsPlayerMoving`为真，就命名为“移动失败”；火焰冲击这类瞬发也会被如此记录。它证明收到失败时检测到移动，不证明移动导致失败，不能据此推断公共冷却、范围或其他真实错误原因。

下一步应让已确认不能起手的读条等待移动条件解除，再及时重算；能够移动施放的技能继续参与实时选择。对没有精确当前起始的同ID失败，不能仅凭移动状态就当作当前请求的失败去反复切换代次。真实失败仍保留重试保护，不应全局把间隔改为0。
