# 后续派发节奏与联合测试

日期：2026-11-09。继承[第一阶段](DISPATCH_TIMING_V1.md)，用户要求后续功能一起实现、部署后联合测试；不提交、不推送，版本保持2.0.1。

## 实现范围与边界

- P5：目标变化立即撤回尚未起手请求并使推荐失效。已经起手的技能保留身份直至终态，精确成功仍归属旧目标的起手上下文；不会消耗新目标的按目标额度。等当前施法结束，再进行重算或目标循环重置。收到真实失败则按既有重试规则处理。
- P6：完成联合测试所需的参数、窗口及延迟诊断；实际游戏观察、无缝衔接效果与最终参数尚待用户测试，不能标记为实机调参完成。
- P7：新增独立的技能组排队开关，默认关闭。允许组内普通读条尾部接续下一步，也可在同一组内接续下一轮；只有当前技能精确成功才推进轮数，保留第二次起始及成功身份。最后一轮不跨到父列表提前派发；保持条件、目标、范围、资源或身份未知仍阻断。
- 引导末尾介入：独立开关默认关闭，提前量默认0.05秒，可配置0～0.50秒，0表示等待自然结束。必须有已接受的精确成功及匹配的引导起始身份，并且客户端公开当前引导ID、起止时间。没有成功、起始不匹配、信息受限或时钟未知时均不介入。当前引导尚未成功时，不因为接近结束便推测成功。

引导提前介入可能截断最后一跳，并非保证服务器预载而不打断。公开接口提供引导起止时间，但并不提供本项目可用的“最后一跳已经结算”证明，因此本实现不作此保证；建议从50毫秒开始，结合实际伤害跳数检验。[客户端引导接口定义](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_APIDocumentationGenerated/UnitDocumentation.lua)

## 客户端窗口和网络延迟

每次门禁读取客户端实际 `SpellQueueWindow`，不写入、不覆盖、不把400毫秒作为缺失时的补值。客户端返回0、缺失、受限或不合法时不提前排队。

普通读条窗口：

```text
延迟估计 = min(世界往返延迟 / 2, 150毫秒)
实际提前量 = min(客户端SpellQueueWindow, 500毫秒, 用户提前量 + 延迟估计)
```

世界延迟缺失时额外补偿为0，仍遵守客户端公开窗口。网络采样复用现有调用，最多每秒刷新一次；世界往返延迟的一半只是传输参考估计，并不保证等于单向延迟，不随机化按键时间。可以独立关闭网络补偿。

引导窗口：

```text
实际引导提前量 = min(客户端SpellQueueWindow, 500毫秒, 用户引导提前量)
```

网络延迟只显示在引导诊断中，不扩大用户允许的末尾截断预算。日志保留客户端窗口、剩余时间、实际提前量、世界／本地延迟及额外补偿。`GetNetStats`的世界与本地延迟分别读取，不把本地延迟替代世界延迟。[客户端网络状态显示源码](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_PerformanceBar/PerformanceBar.lua)

## 设置及测试顺序

1. `/reload` 后先维持旧开关，确认普通列表、APL及魔杖行为没有变化。普通末尾排队仍由原开关控制，不查询GCD/61304。
2. 普通读条开启末尾排队，先设0.20秒；对照诊断中的实际客户端窗口、世界延迟与补偿后提前量，不假定客户端一定为400毫秒。
3. 开启技能组内读条末尾排队，使用两步、两轮的组；检查同ID／不同ID、组内换步与跨轮，以及最后一轮返回父列表。轮数和次数必须由实际成功推进。
4. 引导提前介入单独开启，提前量先设0.05秒；比较关闭、50毫秒与100毫秒时的最后一跳和接续间隔。若最后一跳受影响，调低或设0；不得据此宣称已经无损衔接。
5. 单独启用引导开关不足以提前介入组内引导；组内还需启用技能组开关。维护不使用引导提前介入；魔杖和自动攻击继续沿用既有开启状态保护。
6. 分别在未起手、已起手及组内切目标，检查旧回执保留、新目标不被旧成功消耗额度，以及目标循环重置时机。测试失败、移动、Secret、丢失目标和隐藏CDM。
7. 测试后 `/reload` 或退出游戏落盘，再核对 `queueDiagnostics` 的阶段、窗口、网络采样、请求及精确身份。离线模拟、部署哈希和日志请求不证明真实输入或服务器施法成功。

无需增加第二个输入程序，不新增计时器、钩子、GCD查询或宏，不修改技能绑定及WTF。活动TEK不停止、不替换。
